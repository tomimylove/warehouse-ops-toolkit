# Архитектура и решения

## 1. Технологический стек

| Слой | Технология | Причина |
|---|---|---|
| Frontend | React + TypeScript | Стандарт индустрии, максимум community/AI-поддержки |
| Backend | NestJS (Node.js/TypeScript) | Архитектурно близок к ASP.NET Core (модули/DI/DTO/guards) — облегчает перенос в другой стек при необходимости; один язык с фронтендом ускоряет разработку |
| ORM | Prisma | Генерирует настоящие Postgres DDL-миграции — схема БД сразу в целевом диалекте, без перевода |
| БД (разработка/демо) | Postgres, free tier (Supabase/Neon) | Изначально был Azure SQL free tier — отказались: регистрация упиралась в Azure AD tenant-ошибки, не связанные с самим приложением (см. ниже, раздел 13). Supabase/Neon — вход по email/GitHub, без tenant'ов, оба бесплатны навсегда на небольшом масштабе |
| Хостинг frontend | Netlify | Автодеплой по пушу в GitHub |
| Хостинг backend | Netlify Functions (предпочтительно) или Render (запасной вариант) | Netlify Functions держит всё на одном домене; Render как альтернатива, если возможностей функций не хватит |
| Репозиторий | GitHub, публичный | Проект generic, без конфиденциальных данных — публичность безопасна и открывает бесплатный Netlify/Pages без ограничений приватных репозиториев |
| Авторизация (прототип) | JWT, изолированный в отдельном `AuthModule` | Модуль изолирован, чтобы заменить схему авторизации без переписывания бизнес-логики |
| CI/CD | GitHub Actions (тесты/линт/typecheck) + Netlify auto-deploy | Тесты — на каждый push/PR, деплой — автоматом при мерже |

**Архитектурный стиль: модульный монолит, не микросервисы.** Один процесс,
чёткое разделение по NestJS-модулям на уровне кода — вся организационная
польза микросервисов без операционной сложности, неоправданной на текущем
масштабе.

## 2. Backend-agnostic слой данных

```ts
interface DataProvider {
  list(entity: string): Promise<Record[]>;
  get(entity: string, id: string): Promise<Record>;
  create(entity: string, data: Record): Promise<Record>;
  update(entity: string, id: string, data: Record): Promise<Record>;
  remove(entity: string, id: string): Promise<void>;
}
```

- `RestApiProvider` — реализуется полностью, основной путь.
- Альтернативные провайдеры (например, для платформенных списков/таблиц
  стороннего хостинга) — описываются как контракт при необходимости, без
  обязательной немедленной реализации.

UI не знает, какой backend подключён — при необходимости переключается
сменой одной реализации, без переписывания экранов.

## 3. Автоматизация уведомлений — только вспомогательная роль

Внешние low-code инструменты автоматизации (если используются) — только для
уведомлений (например, в чат/мессенджер), не для CRUD-операций приложения.
Асинхронные HTTP-триггеры такого типа сервисов дают задержку и подвержены
лимитам — непригодны как основной путь данных.

## 5. Digital Twin — терминология и архитектура

- **Digital Twin** — модуль/раздел приложения.
- **Views** (Виды) — переключаемые режимы представления одного и того же
  физического объекта:
  - **Фотоплан** — аннотирование фото местности/помещения: инструменты
    рулетка (расстояние), площадь (полигон), маркеры — на отдельных слоях
    поверх изображения.
  - **Изометрическая схема** — параметрический изометрический редактор
    (сетка, каталог объектов, стеллажи с адресуемыми ячейками).
- Полноценное 3D — не используется: изометрика даёт сопоставимый визуальный
  эффект глубины на порядок дешевле в разработке и поддержке.

**Разделение:**
- Backend: отдельные NestJS-модули `PhotoPlanModule` и `IsometricModule`,
  разные модели данных, общая только ссылка на сущность `Site`.
- Frontend: общий "shell" (переключатель Views, общие элементы дизайн-
  системы), но реализация каждого View — отдельная, не делящая состояние.

### Три категории объектов на изометрической схеме

| Категория | Пример | Хранение | Рендер |
|---|---|---|---|
| Зоны | Стены, полы, проходы | Геометрия (полигон + цвет) | Код (rect/polygon) |
| Дискретные объекты | Погрузчик, паллета, дверь | Иконка + позиция + ориентация | Готовый спрайт (PNG/WebP) |
| Составные структуры | Стеллаж | Параметры (bays×levels) + массив ячеек с данными | Генератор из иконок-деталей + клик-математика по сетке |

- Ячейки стеллажа — адресуемые под-объекты, с привязанными данными и
  закраской по заполненности (heatmap поверх схемы).
- Импорт CSV → автогенерация схемы: точный формат CSV и обработка
  нестандартных конфигураций стеллажей — решается на этапе проектирования
  этого модуля. Вероятно понадобится гранулярный формат (строка = ячейка,
  а не строка = стеллаж целиком), так как реальные выгрузки складских систем
  обычно устроены именно так.

### Иконки

- Формат — PNG/WebP; SVG не обязателен и не годится для детализированного/
  фотореалистичного стиля.
- Источник — готовый лицензированный набор, не рисуется вручную с нуля.
- Производительность с растровыми иконками не проблема при переиспользовании
  одного файла на много экземпляров + (при больших объёмах) рендер через
  `<canvas>` вместо множества DOM-элементов.

## 6. Окружения (dev/test/live)

- `dev` — только режим локальной разработки, не деплоится отдельным пакетом.
- `test` и `live` — отдельные сборки/окружения, переключаемые одной
  переменной (`APP_ENV`) в конфиг-модуле, не правкой кода.
- Схема БД создаётся/обновляется через provisioning-скрипт, а не руками,
  чтобы dev/test/live не расходились по структуре.

## 7. Стоимость — контрольная сводка

| Сервис | Бесплатный лимит | При превышении |
|---|---|---|
| GitHub (публичный) | без ограничений | — |
| Netlify | 300 кредитов/мес (~15 ГБ) | Пауза сайта, не счёт |
| Render (если используется) | 750 инстанс-часов/мес | Пауза, не счёт |
| Supabase/Neon free tier (Postgres) | 500 МБ–0.5 ГБ в зависимости от провайдера | Проект приостанавливается при неактивности (free tier), не списание денег — оба провайдера без привязки карты на бесплатном тире |

При реалистичной нагрузке прототипа весь стек укладывается в бесплатные
лимиты.

## 8. Процесс разработки — по модулям

1. Дизайн-система (цвета, типографика, компоненты) — до первого экрана
   любого модуля.
2. Core-слой: справочники, роли/права, инфраструктура уведомлений.
3. На каждый модуль — цикл:
   - сводка текущего понимания требований;
   - вопросы: что оставляем, что меняем, что добавляем нового благодаря
     стеку;
   - feature-спека;
   - макет на основе дизайн-системы;
   - реализация (схема → API → UI);
   - деплой, демонстрация, правки.
4. Порядок модулей: Announcements (простой, обкатать процесс) → далее по
   приоритету; Digital Twin — отдельно спроектированный сложный модуль.

## 9. Обезличивание

- Никаких названий организаций, реальных объектов/адресов — нигде: код,
  README, UI-тексты, commit-сообщения, changelog.
- Тестовые/демо-данные — только вымышленные.
- Реальные внутренние процессные детали (коды систем учёта, орг-структура) —
  обобщаются или не переносятся.

## 11. Права доступа — гранулярный RBAC, не admin/editor/reader

По прямому запросу — фиксированные роли-уровни (admin/editor/reader,
FSA-наследие) отклонены. Вместо них:

- `Role` — просто именованный набор ключей-разрешений (`RolePermission`).
  Ключ — свободная строка `"<module>:<action>"` (`"announcements:pin"`,
  `"hse:edit"` и т.д.), не enum — новое разрешение добавляется сидом
  данных, не миграцией схемы.
- `User` привязан к ровно одной `Role`. Реальный пользователь — любой
  Azure AD аккаунт (когда подключим аутентификацию).
- **Роль "Default"** (`Role.isDefault: true`, сидируется в `prisma/seed.ts`)
  — обычная, редактируемая роль (переименовать/поменять набор разрешений
  можно как у любой другой), с одной особенностью: её автоматически
  получает любой новый пользователь при первом обращении
  (`UsersService.findOrCreateByEmail`) — никто не остаётся вообще без
  роли. Дальше роль можно сменить вручную (будущий Admin-модуль — простой
  `User.roleId` update).
- **Отсутствие разрешения — не просто скрытая кнопка.** Нет
  `"<module>:view"` → пункт меню не показывается (`apps/web/src/app/
  AppSidebar.tsx`) И прямой переход по URL блокируется тем же ключом
  (`RequirePermission` вокруг каждого `<Route>` в `App.tsx`). Проверка на
  бэкенде (`PermissionsGuard` + `@RequirePermission()`) — обязательна для
  каждого мутирующего эндпоинта, фронтовая проверка — только UX, не
  граница безопасности.
- Действие внутри одного эндпоинта может требовать сразу двух ключей —
  например, `PATCH /announcements/:id` проверяет `announcements:edit`
  через guard и дополнительно `announcements:pin`, если меняется именно
  `pinned` (см. `AnnouncementsController.update()`) — редактировать текст
  и закреплять анонс для всех может быть разными правами.
- До подключения Azure AD — `CurrentUserService` всегда резолвит одного
  захардкоженного dev-юзера (`prisma/seed.ts`, роль "Administrator" со
  всеми текущими ключами). Контракт (`GET /me` → `{id, email, name,
  permissions}`) уже реальный — подключение Azure AD меняет только то,
  как `CurrentUserService` находит пользователя, не сам контракт и не
  что-либо на фронте.

## 12. Навигация 2.0 — реструктуризация по мотивам YouGile

По прямому запросу — пересмотр состава и группировки пунктов сайдбара до
того, как в них вложена реализация (Projects/Planner/HSE/Handover ещё
placeholder), опираясь на изученный интерфейс YouGile (задача-как-чат,
drawer вместо перехода на отдельную страницу). Стиль (shadcn) не меняется,
меняется только структура и модель данных задач/досок.

### Новая структура сайдбара

1. **Announcements** — без изменений, термин остаётся (не "Activity"/
   "Feed" — не нашлось причины менять, кроме вкусовщины). Сторис
   инцидентов и виджеты — не трогаем, killer feature. Полный текст анонса
   открывается через `EntityDrawer` (см. ниже), не переходом на отдельную
   страницу — обсуждение показывается внизу того же дравера после текста.
2. **Operations** (группа, заменяет прежние Warehouse+HSE+Dashboards+Links
   по отдельности) — HSE, Staff, Weekly meeting, Digital twin, Dashboards,
   Links. Всё это "управление складом", в отличие от Admin ("управление
   приложением").
   - **Weekly meeting** — пока просто placeholder, идея зафиксирована на
     будущее: не форма ввода, а обзорный инструмент/ретроспектива —
     собирает задачи/доски/проекты на одном экране, чтобы видеть картину
     целиком. К реализации не приступать, пока не обсудим отдельно.
3. **Tasks** (заменяет Projects и Planner как отдельные пункты) — единый
   инструмент, модель данных и UI — см. ниже.
4. **Knowledge base** — без изменений, отдельный пункт.
5. **Profile** — новый пункт (сейчас в сайдбаре его не было вообще).
   Не "страница настроек аккаунта", а личный рабочий хаб/фокус-режим: мои
   задачи (фильтр по Tasks), Handover как раздел внутри (не отдельный
   пункт меню — реальная операция передачи смены не должна теряться, но
   и не заслуживает отдельного места в общем меню), моя активность.
6. **Admin** — без изменений, "управление приложением". Когда дойдём до
   реализации — часть данных (справочники объектов/ячеек) может
   переехать в Operations, если окажется, что это данные склада, а не
   системная конфигурация.

**Notes** сознательно НЕ пункт сайдбара — открывается через кнопку
"быстрая заметка" (плюсик, есть в сайдбаре уже сейчас) как `Sheet`
(drawer): список всех личных заметок сверху, форма быстрого добавления
внизу. Счётчик заметок — бейдж на самой кнопке, не отдельная строка меню.

### Модель данных Tasks (по образцу YouGile)

Иерархия — **`Project → Board (вкладки) → Column → Task`**, не
"доска = проект". Внутри проекта можно завести несколько досок
(YouGile показывает их вкладками над списком задач, "+" рядом с
последней — новая доска на месте) — это и есть замена "категорий":
категория = отдельная доска, не колонка и не тег.

`Task` — одна сущность на все случаи, не разные таблицы под Projects и
под личные заметки:
- `boardId` пусто → это личная заметка (Notes), видна только автору.
- `boardId` заполнено → обычная задача на доске проекта, показывается
  через `Board`/`Gantt`/`Calendar` — три **view одного и того же набора
  задач**, переключаются табами, не три отдельных модуля.
- Перевести заметку в задачу проекта — просто проставить `boardId`
  (и `columnId`), без миграции данных между разными механизмами.

### EntityDrawer — общий Core-примитив, не только для задач

Правая выезжающая панель (`Sheet`) с конфигурируемым набором вкладок —
общий компонент, не специфичный для Tasks:
- Задача: Chat / Info-Log / Description / Subtasks.
- Анонс: полный текст + обсуждение внизу (тот же `bubble`-компонент чата,
  что у задач).
- Позже — любая другая сущность, которой понадобится похожий паттерн
  (карточка объекта Digital Twin, запись Staff и т.д.), переиспользует
  этот же примитив, а не копирует вёрстку.

Комментарии/чат — тоже общий примитив (уже фиксировали раньше), и сразу
закладываем в него **упоминания через `@`** с уведомлением упомянутого —
не как отдельную доработку поверх, а как часть исходного дизайна
механизма.

### Порядок реализации

Раз цель — "сначала универсальные модули, потом специфичные", Tasks (и
бесплатный побочный эффект — Notes) реализуется раньше доработки
Announcements под `EntityDrawer` — общий примитив появляется на Tasks,
Announcements переезжает на него же следующим шагом, не наоборот.

### Правки после первого прохода (по скриншотам FSA/YouGile)

- **Notes — плавающая круглая кнопка ("+"), не пункт сайдбара и не
  футер-кнопка.** `QuickNoteFab` рендерится на уровне `AppShell`
  (`position: fixed`, правый нижний угол), видна на любом экране — прямое
  продолжение FSA-паттерна "Quick add task" (та же позиция, тот же смысл),
  просто открывает `Sheet` вместо модалки.

## 13. БД: Azure SQL → Postgres (Supabase/Neon)

Изначальный выбор (раздел 1) был Azure SQL free tier — настоящий SQL
Server, щедрый бесплатный лимит навсегда. На практике регистрация
застряла на уровне самого Azure AD, не приложения: личный
(`live.com`/`outlook.com`) аккаунт получал `AADSTS16000` — портал пытался
аутентифицировать его против чужого tenant'а ("Microsoft Services"),
устойчиво воспроизводилось и в обычном окне, и в инкогнито, и с разных
устройств. Похоже на тот самый bleed-through корпоративного контекста,
которого и опасались с самого начала проекта (раздел 9, обезличивание) —
только тут он заблокировал не данные, а саму возможность завести
ресурс.

**Решение — перейти на Postgres**, free tier у Supabase или Neon:
регистрация по email/GitHub, без AAD tenant'ов. Заодно упростило схему —
SQL Server запрещает несколько cascade-путей в одну таблицу (из-за чего
в `Task` появились `NoAction`-костыли под `boardId`/`columnId`/`parentId`
при первой реализации Tasks), Postgres это разрешает — связи в
`schema.prisma` вернулись к обычным `Cascade`/`SetNull`, без обходных
путей.

Собственно бизнес-логика (Prisma-модели, NestJS-сервисы, фронт) не
менялась вообще — только `datasource.provider` в `schema.prisma` и
удаление SQL-Server-специфичных `@db.NVarChar`. Это и была цель
`DataProvider`-подобной изоляции с самого начала: смена нижнего слоя не
должна задевать то, что выше.
